1. Goal and scope

The earlier part of Phase 1 delivered query_metrics(). This phase completes the observability tool layer that the future investigation agents will call:

  • search_logs() searches OpenSearch by service, level, time range, text (and trace ID), returning summaries.
  • get_traces() searches Jaeger by service, operation, error status, time range (and min duration, or one trace ID), returning trace IDs, failed services, relevant spans and duration summaries.
  • filters.py sanitizes all telemetry so no feature-flag (fault-injection) state reaches callers.
  • Integration with, and review of, query_metrics().

Constraints: strictly read-only; URLs from environment variables; structured summaries, not dumps; tests on recorded responses plus live integration tests; no AI agents and no Google ADK yet. The tools are plain functions with signatures an agent framework can register later.

4. Architecture

Why shared modules? A security property like "no tool can POST" or "no flag string leaves" is only credible if it lives in one place and is tested once for all tools. Adding a fourth tool means writing a summariser and an allow-list, not new HTTP or filtering code.

5. Security model: feature-flag isolation

Threat: the diagnosis agent must find the cause of an injected fault from symptoms. If any tool output contains a flag key, variant or the flag service's behaviour, the agent can "diagnose" by reading the answer. Goal: keep every symptom, remove every reference to the mechanism.

LayerRuleWhy
1 · InputsRefuse any service/operation/text/PromQL mentioning flags, the flag service or a flag key, before a request is madeOtherwise result counts become an oracle ("how many logs mention cartFailure?")
2 · Flag service trafficDrop spans/logs from flagd/flagd-ui and any span or log talking to it (flagd, flagservice, ofrep, openfeature in name or attribute values)The evaluation calls themselves reveal which flags are consulted
3 · Flag attributes/eventsRemove feature_flag.*, demo.feature_flag.*, shipping.feature_flag.*, feature_flag_key… at any depth; drop events named after flagsThey carry key, variant and value
4 · TextReplace any flag-revealing string as a whole with [redacted] (label sets in Prometheus messages are redacted individually)"…due to [redacted]" would still reveal the cause
5 · Logs vs spansLogs whose message/event concerns flags are dropped (narration); organic error logs carrying flag text only in an attribute value are kept, value redacted. Spans are kept and stripped.Keep symptoms (frontend HTTP 500, payment errors), drop the narration
6 · Server sideOpenSearch must_not excludes the same records inside the queryCounts/aggregations stay consistent with the records shown
7 · Final scrubscrub_output() walks every result: drops flag-named keys, redacts stringsDefence in depth against bugs in layers 2–6
Verified on real faultsFrom 20:50 to 20:59 UTC on 20 Nov 2026, productCatalogFailure, paymentFailure=50%, adManualGc and intlShippingSlowdown=5sec were active. The raw product-catalog Jaeger response contained feature_flag 175× and productCatalogFailure 20×; the raw logs contained the ad and shipping narration verbatim. Every tool output contained 0 flag mentions, while still showing payment error ratio 0 → 0.5, payment :: charge and product-catalog :: GetProduct as error origins, product OLJCESPC7Z, frontend HTTP 500s and the ad service's GC pauses ("artificially triggered GCs took: 1016 ms").
Residual risks (accepted, D-210)Aggregate volumes that include flag-evaluation work still move slightly; pattern matching is heuristic (re-record fault fixtures after demo upgrades); flagd and other services remain on random 0.0.0.0 host ports upstream, so the future agents must not receive a generic HTTP or shell tool.

7. get_traces (Jaeger)

get_traces(service=None, operation=None, errors_only=False, minutes=15, limit=10,
           min_duration_ms=None, trace_id=None) -> dict

Requests: GET /api/traces?service&operation&start&end(µs)&limit(2×)&tags={"error":"true"}&minDuration=Nms, or GET /api/traces/<16–32 hex>. Over-fetching 2× compensates for traces that sanitization removes.

Per trace: trace_id, start, duration_ms (over visible spans, so flagd's 600 s EventStreams no longer inflate it), root_service/root_operation, span_count, services, error_span_count, failed_services, error_origins, relevant_spans (≤ 5; ≤ 15 for a single trace), and incomplete when spans are still arriving.

Summary: trace and error-trace counts, incomplete_trace_count, duration min/p50/p95/max/mean (nearest-rank percentiles), failed services, error origins and root operations, each counted.

ConceptDefinition and why
Error originAn error span with no failing descendant. Errors propagate up the call chain (payment → checkout → frontend → proxy), so the deepest failing span is the best first guess at where the fault lives.
Self timeSpan duration minus the union of its children's intervals. Total duration always favours the root and proxy hops; self time shows where time is actually spent (live example: email send_email, 10.6 ms of 11.1 ms).
Error re-evaluationJaeger's error=true matches traces with any error span. After sanitization, a trace whose only errors were flagd spans is not an error trace. A trace made only of flagd traffic disappears entirely.
IncompleteRaw spans referencing parents Jaeger has not received yet (counted before sanitization, so removed flag spans don't trigger it). Found in a recording made seconds after the requests: 45 spans, 9 dangling parents, origins one level too high.

8. query_metrics: integration and changes

  • Now uses _http.get_json and filters; its guard additionally refuses flag key names and ofrep; its output passes through scrub_output.
  • Signature change: the test-only client: httpx.Client parameter is gone, because an agent framework would expose it to the LLM. Now query_metrics(promql, minutes, max_series=20), with max_series bounded 1–200.
  • The refusal message is neutral ("This query targets restricted telemetry and is not permitted.") and no longer contains the words "feature flags".
  • Redaction is stricter: if flag text remains outside a label set, the whole message is withheld.
  • All 79 original metrics tests still pass after a mechanical migration.

11. Testing

Strategy

  • Network blocked by default. An autouse fixture replaces _http.make_client with a transport that fails the test, and clears all copilot environment variables, so unit tests can't depend on the developer's shell.
  • Fixtures from the real tools. record_tool_fixtures.py runs each tool through a recording transport and stores the exact request and the raw response. Raw recordings bypass server-side exclusions to prove the client-side defences.
  • Real faults. Fault-state fixtures were recorded with four flags active (D-207).
  • Invariants over the whole corpus. No flag text in any output (the corpus itself is checked to contain flag data, so the test can't pass vacuously); exactly one GET per call; strict JSON; never raising on hostile input; ADK-ready signatures.
  • Live tests auto-skip per backend; they include trace → logs correlation and a leak sweep across 15 services (48 tool calls).

14. Interview questions

1. Why centralise HTTP and sanitization instead of writing them per tool?
Security properties need one enforcement point. "Only GET" is a single allow-listed function, and "no flag strings" is one policy plus a final scrub. Both are tested once for all tools, with AST and corpus-wide invariant tests.
2. How do you make a tool read-only when OpenSearch search normally uses POST?
OpenSearch accepts a request body on GET _search. Using it keeps the whole package GET-only, which a test enforces by scanning for write verbs.
3. Why redact whole strings rather than just the flag words?
"Delaying international shipment due to [redacted] [redacted]" still tells the agent the cause is a deliberate toggle. Whole-string replacement removes the mechanism and keeps the structural symptom (error status, timing).
4. Why drop some logs but keep spans?
A span is a unit of real work whose timing and status are organic symptoms. A log that talks about a flag is narration of the injection. Organic error logs that merely carry flag text in an attribute are kept with that value redacted, which also keeps counts consistent.
5. What is a counting side channel and how did you close it?
If hidden records are still counted, totals reveal them (19 matches but 8 shown). Fix: exclude the same records inside the OpenSearch query, refuse flag-related inputs, and never report how many items were hidden.
6. How do you identify where an error originated in a trace?
Errors propagate upward, so the deepest error span with no failing descendant is the origin. It is only reliable on complete traces, so the tool flags traces whose spans reference parents that haven't arrived yet.
7. What is self time, and why rank by it?
Duration minus the union of child intervals. A parent's total duration always includes its children, so ranking by duration always surfaces the root; self time surfaces the span actually doing work.
8. Why query Jaeger directly instead of through the demo's proxy?
Envoy traces every request, so the copilot's own queries would appear as frontend-proxy traffic, which is the observer affecting the observed. Direct loopback access avoids it.
9. Why did @timestamp break time filtering, and what did you use instead?
Rust and C++ SDK logs arrived without a timestamp, so it defaulted to the epoch. observedTimestamp is set by the Collector on receipt and is always present.
10. How do you prove a sanitizer works, rather than hope?
Record real data while faults are active, keep raw recordings that bypass server-side filters, assert the corpus really contains flag data, then assert that every tool output over every fixture contains none. Repeat live across all services.
11. How do you keep tests hermetic yet realistic?
Block the network and clear the environment by default; replay recorded responses at the transport layer while capturing outgoing requests; add live tests that skip when backends are absent.
12. Why do tool signatures matter before any agent exists?
Frameworks like Google ADK generate tool schemas from signatures and docstrings. A client parameter would be shown to the LLM, and complex types break schema generation. A test now enforces simple types and documented parameters.
13. What would you change for production?
Enforce isolation at a telemetry gateway in front of all stores (not only per tool), authenticated backends, connection pooling and caching, retries with backoff for idempotent 503s, and metrics about the tools themselves.
14. What did the fault-injection exercise teach you about operations?
Configuration reload mechanisms matter: flagd syncs on modification time, so restoring a file with its old mtime left faults active silently. A fault harness must verify behaviour, not just file content.

15. Limitations, files and next steps

  • Pattern grouping uses a 200-record sample, so counts per pattern are sample counts (totals come from OpenSearch).
  • Error origins are a heuristic (deepest failing span). Asynchronous Kafka paths may appear as separate traces.
  • Text-pattern sanitization must be re-validated after demo upgrades (record_tool_fixtures.py fault).
  • No Git commit was made: the project root is still not a Git repository (D-110, D-210).
