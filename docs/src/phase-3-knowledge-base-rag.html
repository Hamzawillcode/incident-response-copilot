1. The idea in one minute

In Weeks 1 and 2 the copilot learned to look (read metrics, logs and traces) and to think (a Gemini agent that follows evidence). But it had no memory. A real on-call engineer also asks: "Have we seen this before? What does the runbook say?"

This week we gave the copilot the team's written knowledge:

  • Runbooks: instruction pages, "if you see X, check Y, then do Z". We wrote 14, one per part of the shop.
  • Postmortems: write-ups of past incidents, "what happened, why, how we fixed it". We wrote 5 seed examples.
  • Search tools the agent can call: search_runbooks and search_postmortems. They find the right page from a plain description of symptoms.

This pattern is called RAG (Retrieval-Augmented Generation): first retrieve relevant documents, then let the LLM generate its answer using them.

AnalogyBefore, the copilot was a smart doctor with no access to the hospital's files. Now it can search the procedure manual (runbooks) and the patient history of similar cases (postmortems), but it still has to examine this patient (telemetry) before deciding.

3. Agents and tools this week

New agents: none

The guide adds the Knowledge (RAG) agent in Week 4, when the single agent is split into a Coordinator with sub-agents. This week the existing diagnosis agent gets an optional knowledge mode instead: build_diagnosis_agent(knowledge=True) or run_diagnosis.py --knowledge.

New tools: 2 (7 in total)

search_runbooks(query, k=4) and search_postmortems(query, k=3). With the 5 telemetry tools from Weeks 1–2 (get_service_health, get_service_metrics, get_traces, search_logs, query_metrics) the agent has 7 tools in knowledge mode.
Why keep the default agent unchanged?The guide's evaluation compares "single agent, no RAG" with "single agent + RAG" and "multi-agent + RAG" (an ablation). If RAG were always on, we could never measure what it adds. So knowledge mode is a switch, and the default stays the Week-2 agent.

5. The knowledge: runbooks and postmortems

Runbooks (14)

One per part of the shop: checkout, payment, product-catalog, cart, recommendation, ad, kafka consumers, shipping and quote, email, currency, frontend/proxy/images, traffic spike, plus two general ones: "triage: symptom vs. cause" (who calls whom) and "known noise and false alarms". Each has the same sections: Overview, Symptoms, Diagnosis, Common causes, Remediation, Verification.

---
# Payment service: charge failures and outages

## Symptoms
- Payment logs its failures as warnings, for example "Payment request failed ...".
  Search with `level="warn"`, not `level="error"`.
...
Lesson: check every name against the real systemA runbook that names a wrong metric sends the agent to a query that returns nothing, and "no data" can look like "nothing is wrong" (the Week-2 trap). So every metric, span and attribute name was checked against the demo's source code or our recorded data. Example: the product ID on spans is demo.product.id, not app.product.id as one might guess.

That separation is honest: a matching postmortem makes a fault easier, and we want to see by how much.

6. From Markdown to searchable chunks

We do not store whole files. Each ## section becomes one chunk:

runbook/payment#00-overview        269 chars
runbook/payment#01-symptoms        453 chars
runbook/payment#02-diagnosis       833 chars
runbook/payment#03-common-causes   316 chars
runbook/payment#04-remediation     313 chars
runbook/payment#05-verification    154 chars
  • Why sections? "Symptoms" or "Remediation" is exactly the unit someone needs. A whole file would dilute the match and waste tokens. Fixed 500-character windows would cut a numbered procedure in half.
  • Context travels with the chunk. What gets embedded is title + heading + text, for example "Payment service: charge failures and outages / Remediation / ...". A section that just says "Roll back the change" means nothing without its title.
  • Long sections (over 1,500 characters) are split at blank lines, never inside a code block. Every chunk has a stable ID and a content hash, which drives incremental updates (section 9).

7. Embeddings: turning text into numbers

An embedding is a list of numbers (here 768) that represents the meaning of a text. Texts with similar meaning get similar lists, even when they share no words. "Customers cannot pay" and "payment charge failures" end up close together.

ChoiceWhy
gemini-embedding-001Same provider as the agent's LLM, free tier, configurable (KB_EMBEDDING_MODEL).
Two task typesSections use RETRIEVAL_DOCUMENT, questions use RETRIEVAL_QUERY. The model is trained for this "short question vs. long paragraph" case.
768 dimensionsThe default is 3072. The model is trained so a shorter prefix still works (Matryoshka). 768 is 4 times smaller and fits pgvector's 2,000-dimension index limit. Shortened vectors are re-normalised to length 1.
Model stored per rowVectors from two different models are not comparable. Search only compares rows from the query's model, and ingestion re-embeds when the model changes.
Batches and retriesIngestion sends 50 texts per request and retries rate limits (back-off of 2, 4 and 8 s). Query embedding makes one attempt with a 10 s timeout (an incident must not wait) and keeps a 256-entry cache.

8. Hybrid search: keyword + vector + RRF

Each tool call runs two searches and merges them:

Keyword search (Postgres full text)

Finds exact words: service names, operation names, error messages. Words are stemmed ("errors" → "error"), stop words dropped, and any word may match (OR), because a symptom description should not need every word. Words in the title and headings count most.

Vector search (pgvector)

Embeds the query and finds the sections whose embeddings are closest (cosine distance, <=>). Finds paraphrases. With 116 rows an exact scan takes about a millisecond, so no approximate index is needed yet.

Merging with Reciprocal Rank Fusion (RRF)

The two searches give scores on different scales (a text-rank number vs. a similarity between −1 and 1), so we ignore the scores and use only the ranks:

score(section) = sum over both lists of  1 / (60 + rank in that list)
SectionKeyword rankVector rankRRF score
payment#02-diagnosis121/61 + 1/62 = 0.0325 (found by both: wins)
checkout#01-symptoms—11/61 = 0.0164
cart#03-common-causes2—1/62 = 0.0161

60 is the constant from the original RRF paper (Cormack et al., 2009). It stops a single top hit from one list from dominating.

Then results are grouped by document: the agent gets k different runbooks, each with its 2 best sections, not 4 sections of the same file.

Real output: search_runbooks("checkout errors", k=3) (keyword mode, no key yet)

{"status": "ok", "kind": "runbook", "query": "checkout errors", "retrieval": "keyword", "result_count": 3,
 "results": [
  {"rank": 1, "source": "kb/runbooks/checkout.md", "title": "Checkout: orders failing or slow",
   "score": 0.01639, "services": ["checkout"], "matched_by": ["keyword"],
   "sections": [{"heading": "Symptoms",  "text": "- `POST /api/checkout` errors in `frontend` ..."},
                {"heading": "Diagnosis", "text": "1. Run `get_traces(service=\"checkout\", errors_only=True)` ..."}]},
  {"rank": 2, "source": "kb/runbooks/frontend.md", "score": 0.01493, ...},
  {"rank": 3, "source": "kb/runbooks/known-noise-and-false-alarms.md", "score": 0.01471, ...}],
 "note": "Background knowledge written before this incident. It is not evidence about the current incident: ..."}

0.01639 = 1/61: a section ranked first in one list. frontend's best section was only 7th (0.01493 = 1/67), because the six sections ranked above it all belonged to checkout. Grouping by document lets frontend still appear as the second document.

9. Ingestion: incremental and all-or-nothing

$ python -m copilot.kb.ingest
note: no Gemini key configured (GOOGLE_API_KEY in .env), so sections are stored without
embeddings and searches run keyword-only. Run ingestion again after adding the key.
Ingested 19 documents, 116 sections. Embedding model: none (keyword-only)
  inserted 116, updated 0, unchanged 0, deleted 0, embedded 0
  stored postmortems: 5 documents, 35 sections, 0 with embeddings
  stored runbooks: 14 documents, 81 sections, 0 with embeddings
$ python -m copilot.kb.ingest      # second run: nothing changed, nothing to do
  inserted 0, updated 0, unchanged 116, deleted 0, embedded 0
  • Incremental: each section's content hash is compared with the stored one. Only new or changed sections are embedded, so editing one runbook section costs one API call, not 116.
  • All-or-nothing: embeddings are computed before any write, and all writes happen in one transaction. If the API fails halfway (quota), the database is exactly as before (tested).
  • Text first, vectors later: today the text is stored without vectors. After adding the key, re-running ingestion embeds all 116 sections once.
  • Deleted sections disappear: rows whose section no longer exists are removed in the same transaction.

10. Never block an investigation

The knowledge base is a helper. If it fails, the investigation must continue with telemetry.

SituationWhat the tool does
No Gemini keyKeyword search, retrieval: "keyword"
Embedding API fails during a search (quota, timeout)Keyword search plus a warnings entry
Key present, but sections not yet embedded with this modelKeyword search plus a warning. It does not even embed the query (no wasted API call).
Database downstatus: "error", type connection, with the command to start it. The prompt tells the agent to carry on with telemetry.
Knowledge base never ingestednot_initialized, with the ingest command

For measurements, the explicit modes hybrid and vector raise an error instead of quietly falling back, so a fallback can never distort a result.

11. Safety: read-only, no leaks

RuleHow it is enforced
No answers in the knowledgeIngestion refuses any document line with fault-injection words (same patterns as the telemetry filters) and names file:line. A test scans every file for an even broader pattern (the word "flag" appears nowhere). The tools also refuse such queries and scrub their output.
Searches cannot writeSearch sessions are read-only on the server (default_transaction_read_only=on) with a 5 s statement timeout. A test checks that a DELETE fails. Only ingest.py contains write SQL, and a test checks that too.
No SQL injectionAll values are query parameters. plainto_tsquery ignores search-operator syntax. Hostile queries ('; DROP TABLE ..., operators) are tested against the real database.
Knowledge is not evidenceEvery result carries a note saying so, and the prompt forbids citing documents as evidence.
SecretsThe database password is hidden in error messages (copilot:***@localhost:5433). Gemini API keys are removed from embedding error messages.

12. Measuring retrieval

The guide's Week-3 target: searching "checkout errors" returns the right runbook in the top 3. We went further and wrote 28 test queries (eval/retrieval_queries.yaml), each listing the documents that count as correct: 20 that use words from the right document, and 8 paraphrases that describe the problem in other words.

$ python scripts/check_retrieval.py --mode keyword
MISS [runb/parap] rank=4  'customers cannot pay for their order'
       expected ['payment'], got ['checkout', 'kafka-consumers', 'email']
MISS [runb/parap] rank=5  'the suggestions service uses more and more RAM'
       expected ['recommendation'], got ['cart', 'payment', 'ad']

mode=keyword retrieval=keyword
  all        n=28  hit@1=0.86  hit@3=0.93  MRR=0.90
  keyword    n=20  hit@1=1.00  hit@3=1.00  MRR=1.00
  paraphrase n=8   hit@1=0.50  hit@3=0.75  MRR=0.66

Week-3 check: 'checkout errors' -> checkout runbook in the top 3: PASS
  • hit@3 = share of queries whose correct document is in the top 3. MRR (mean reciprocal rank) = average of 1/rank of the first correct document (1.0 means always first).
  • What the misses show: keyword search cannot connect "pay" with "payment charge" or "RAM" with "memory". That is exactly the gap meaning search (embeddings) should close, and the reason for a hybrid design.
Honest limitsI wrote both the documents and the queries, after reading the documents, so the keyword-style score of 1.00 is optimistic. This is a regression check (does a change make search worse?), not a benchmark. The hybrid numbers do not exist yet because they need the Gemini key. Do not quote any hybrid number until check_retrieval.py --mode hybrid has run.

13. The agent's knowledge mode

build_diagnosis_agent(knowledge=True) attaches the 2 search tools and appends a short prompt section (diagnosis_knowledge.md):

  • Search after the overview, once you know the symptoms. One or two searches are enough.
  • Use runbooks to decide what to check next. Treat a similar postmortem as a hypothesis: the same symptoms can have a different cause this time.
  • Knowledge is not evidence. Every evidence item must still come from metrics, traces or logs about this incident. Times and IDs in postmortems are from the past.
  • List the documents used in the new references field of the answer.

The tool guard follows the attached tools: in default mode a call to search_runbooks is refused as an unknown tool. Both calls still count against the 15-call budget.

Unit tests can never call Gemini or the database: a shared fixture replaces the embedder and blocks connections. Database tests each run in a private schema that is dropped afterwards, and they are skipped automatically when Postgres is not running.

1. A "rebuild" that could have deleted the real knowledge base
The SQL first used the bare table name kb_chunks and relied on Postgres's search path. In a test schema without the table yet, DROP TABLE IF EXISTS kb_chunks would have found public.kb_chunks through the search path and dropped the real table. Found while designing the test fixture. Every statement now names <schema>.kb_chunks, and a test covers rebuild in a private schema.
2. A circular import
copilot.tools imports the new tool, the tool imports copilot.kb, and copilot.kb imports copilot.tools (filters, settings). Fix: the tool imports copilot.kb when it is called, not at module load. Checked by importing every module first, in every order.
3. Tests that tested nothing
One database test edited "Restart payment" in a copy of the runbook, but the text says "restart payment" (lower case), so nothing changed and the test failed for the wrong reason. The test now asserts that its own edit really changed the file. Another test's pattern %false-alarm% also matched the runbook known-noise-and-false-alarms.md. Lesson: a test needs a check that its setup worked.
4. Wrong attribute name (caught before it shipped)
The product-catalog runbook was going to say app.product.id. The demo source uses demo.product.id. A runbook with the wrong name would have sent the agent to an empty query.

15. Status, how to run it, limitations

Honest statusBuilt and tested: 565 tests passed (545 unit + 20 against the real Postgres). Keyword search is measured: the Week-3 target is met ("checkout errors" puts the checkout runbook first). Not yet done, because no Gemini key was configured: embeddings, the hybrid measurement and agent runs with --knowledge. Do not quote hybrid or agent accuracy numbers until those runs exist.

Run it yourself

  1. docker compose up -d kb-postgres starts Postgres + pgvector (loopback only, port 5433).
  2. .venv/bin/python -m copilot.kb.ingest loads the 19 documents. Without a key it stores text only.
  3. .venv/bin/python scripts/check_retrieval.py -v shows the top 3 for all 28 queries.
  4. Add GOOGLE_API_KEY to .env, re-run ingestion (all 116 sections are embedded once), then run check_retrieval.py --mode hybrid and compare with keyword mode.
  5. With the demo running and a fault on: run_diagnosis.py --knowledge --runs 5 vs. run_diagnosis.py --runs 5. That is a first look at what RAG adds.

Limitations (known, planned)

  • The postmortems are invented seed data, and the query set is self-written (section 12).
  • No separate Knowledge agent yet (Week 4), and no automatic "write a postmortem after each incident" (Week 4 Action agent, after human approval).
  • The read-only setting is a session default. A dedicated read-only database role is the Week-6 hardening for Cloud SQL.
  • Keyword ranking has no word-rarity weighting (BM25-style IDF). Title weighting compensates on this small corpus. Revisit if the knowledge base grows.

16. Interview questions and answers

What is RAG and why does an incident copilot need it?
Retrieval-Augmented Generation: search your own documents first, then let the LLM answer with what it found. The fix for many incidents is already written down in a runbook or an old postmortem, but nobody remembers where. RAG makes that team knowledge available to the agent in seconds.
Why hybrid search instead of only vectors?
They fail differently. Keyword search is precise on exact names (valkey-cart, oteldemo.PaymentService/Charge) but misses paraphrases: my measurement shows paraphrase hit@3 of 0.75 vs. 1.00 for queries that share words. Vector search handles paraphrases but is weaker on exact identifiers and harder to explain. RRF combines the two using only ranks, so no score calibration is needed.
How did you chunk the documents?
One chunk per ## section, with the title and heading added to the embedded text. Sections are the natural unit (Symptoms, Diagnosis, Remediation), so the agent gets complete procedures rather than fragments. Long sections are split at paragraph boundaries, never inside code.
How do you keep embeddings in sync with the documents?
A content hash per section. Ingestion embeds only new or changed sections, stores the model name per row, re-embeds when the model changes, and writes everything in one transaction after the embedding calls succeed. An unchanged knowledge base costs zero API calls, and a failed run changes nothing.
What if the embedding API is down during an incident?
The search degrades to keyword-only and says so in warnings. If the whole database is down, the tool returns a typed error and the agent continues with telemetry. The knowledge base helps, but it must never block an investigation.
Couldn't the knowledge base leak the answer, like the feature flags in telemetry?
Yes, if a runbook said "switch off the payment-failure flag". So there are three layers: ingestion refuses documents with fault-injection words, a test scans every file for an even broader pattern, and the tools refuse such queries and scrub their output. Separately, I recorded which faults have a similar postmortem so the evaluation can report "seen before" and "never seen" faults separately.
Isn't it cheating to have a postmortem that matches the injected fault?
Real teams do have history, and measuring how much it helps is the point of the RAG ablation. What would be wrong is hiding it. That is why the overlap is documented, some faults have no postmortem, one postmortem is deliberately a lookalike with a different cause, and knowledge can never count as evidence.
How do you make sure the search tool cannot change data?
The search session is read-only on the database server, with a statement timeout. Only the ingestion module contains write SQL, which a test enforces. All values are bound parameters, and I tested hostile input against the real database.
Why pgvector and not a dedicated vector database?
The copilot already needs Postgres for sessions and incidents (Week 4). pgvector adds vector search to the same database: one system to run, real transactions across text and vectors, and SQL filters (kind, model) in the same query. At 116 rows an exact scan is enough. I would add an HNSW index above about 10,000 rows.
How did you measure retrieval quality, and what are the limits?
28 labelled queries, reporting hit@1, hit@3 and MRR, split into keyword-style and paraphrase queries. Keyword-only today: hit@3 = 0.93 overall, 1.00 vs. 0.75 for the two groups. The limit is that I wrote both the documents and the queries, so this is a regression check, not an unbiased benchmark. The hybrid numbers wait for the API key.
What changes for a real customer?
Ingest their runbooks and postmortems (Confluence or Git exports), keep the same chunking, run my query set plus questions from their own past incidents, and give the search tool a read-only database role. Their incident history becomes the evaluation set.
