1. Goal and scope

Phase 1 builds the first tool the copilot's agents will call: a function that answers "what has this metric been doing over the last N minutes?" from Prometheus. The requirements were:

  • connect via PROMETHEUS_URL and use the Prometheus HTTP API;
  • return minimum, maximum, latest value and trend, i.e. a summary rather than raw samples;
  • handle errors, timeouts and empty responses;
  • be strictly read-only;
  • be tested against recorded Prometheus responses wherever possible.

Out of scope: AI agents, and log, trace or other tools. The project's standing security requirement (from Phase 0) also applies: diagnosis must not be able to read feature-flag state.

3. Prometheus concepts you need

Data model

A time series is a metric name plus a unique set of labels, e.g. traces_span_metrics_calls_total{service_name="checkout", span_name="…", status_code="STATUS_CODE_UNSET"}, holding samples (timestamp, float64). Every distinct label combination is a separate series; we saw 5,523 in Phase 0.

TypeMeaningExample from the demo
CounterOnly goes up (resets on restart). Use rate().traces_span_metrics_calls_total
GaugeGoes up and down. Use it directly.container_memory_usage_total_bytes, system_cpu_utilization_ratio
HistogramCumulative _bucket{le=…} counters plus _sum/_count. Use histogram_quantile().traces_span_metrics_duration_milliseconds_bucket

Instant vs range queries

  • /api/v1/query evaluates the expression at one time and returns a vector.
  • /api/v1/query_range evaluates it at every step between start and end and returns a matrix (a list of series, each with values: [[ts, "value"], …]). Values are strings so that "NaN" and "+Inf" survive JSON.
  • For each step, Prometheus looks back up to lookback-delta (5 m here) for the latest sample. That's why a series keeps producing points for up to 5 minutes after its source goes silent.

rate() and window size

rate(x[5m]) computes the per-second increase of a counter using the samples inside the 5-minute window. It needs at least two samples in the window. In this demo samples arrive every 60 s, so [1m] often holds only one and returns nothing (we hit this in Phase 0). Use [2m] at minimum, [5m] to be safe.

How OTLP metrics are named in Prometheus

The Collector pushes OTLP to Prometheus's OTLP receiver. Dots become underscores, units and _total are appended (traces.span.metrics.calls → traces_span_metrics_calls_total), and service.namespace/service.name becomes job="opentelemetry-demo/checkout". Some resource attributes are promoted to labels (service_name, container_name, …).

RED and USE

RED (Rate, Errors, Duration) for request-driven services comes from span metrics. USE (Utilisation, Saturation, Errors) for resources comes from docker_stats and host_metrics. §9 shows one real query of each kind.

7. Code walkthrough

7.1 Public entry point (control flow)

def query_metrics(promql, minutes, *, max_series=20, client=None) -> dict:
    base = {"query": promql, "window_minutes": minutes}
    if problem := _validate(promql, minutes, max_series):   return _error(base, "invalid_input", problem)
    if refusal := _guard_query(promql):                       return _error(base, "forbidden_query", refusal)
    ...                                                       # PROMETHEUS_URL check -> "configuration"
    end = _now(); start = end - minutes*60; step = _step_seconds(minutes)
    params = {"query": promql, "start": ..., "end": ..., "step": str(step), "timeout": "10s"}
    try:
        status_code, body = _get(client, QUERY_RANGE_PATH, params)
    except httpx.TimeoutException:  return _error(base, "timeout", ...)
    except httpx.TransportError:    return _error(base, "connection", ...)
    except _ResponseTooLarge:       return _error(base, "response_too_large", ...)
    return _interpret(base, status_code, body, end, max_series)

(Condensed; see the file for the full version.) The client parameter exists for tests. Production callers use the defaults, and the function then builds and closes its own httpx.Client. The timeout parameter asks Prometheus to abandon the query server-side at the same moment the client would give up, so a slow query doesn't keep running after we've stopped waiting.

7.2 The guard (before any network I/O)

_FLAG_PATTERN  = re.compile(r"feature[\s_.\-]?flag|flagd|flagservice|openfeature", re.IGNORECASE)
_BARE_SELECTOR = re.compile(r"(?:^|[^\w:\s])\s*\{")       # '{' not directly after a metric name

def _guard_query(promql):
    if _FLAG_PATTERN.search(promql):                        # checked on the FULL text, strings included
        return "Queries about feature flags or the flag service are not permitted."
    code = _STRING_LITERAL.sub('""', promql)                 # ignore braces/words inside "..."
    if "__name__" in code:
        return "Selecting metrics by __name__ is not permitted; name the metric explicitly."
    if _BARE_SELECTOR.search(code):
        return "Selectors must start with a metric name, e.g. http_server_request_duration_seconds_count{...}."

The flag check runs on the raw text, so job="opentelemetry-demo/flagd" is caught inside a string. The structural checks run on text with string literals blanked, so http_route="/api/{id}" isn't mistaken for a bare selector (there's a test for exactly that).

7.3 The only network call

def _get(client, path, params):
    if path not in _ALLOWED_GET_PATHS:                      # {"/api/v1/query_range"}
        raise ValueError(f"path {path!r} is not allow-listed")
    with client.stream("GET", path, params=params) as resp:
        ...                                                 # read chunks; abort past 10 MiB
        body = json.loads(raw)  # or the decoded text if it is not JSON (e.g. a proxy's HTML 502)
        return resp.status_code, body

Streaming with a byte cap protects the process from a runaway result (e.g. an un-aggregated selector over all series).

7.4 Interpreting the response

  • Non-JSON body → http_error with a short, redacted snippet.
  • "status": "error" or HTTP ≥ 400 → Prometheus errorType mapped: bad_data→bad_query, execution→query_execution, timeout|canceled→timeout, unavailable, internal→prometheus_internal, anything else → http_error. The message is redacted and capped at 300 characters.
  • warnings and infos (Prometheus 3 puts "might not be a counter" under infos) are redacted and passed through as warnings.
  • Flag-related series are dropped; the rest are summarised, sorted by latest descending, and truncated to max_series. An empty result gives no_data.

7.5 Summarising one series

Each [ts, "value"] pair is parsed; non-finite values (NaN, ±Inf) are counted in non_finite_points and excluded. The summary has min, max, mean, first, latest (with ISO timestamp and age), change, change_percent (null when first is 0) and the trend fields. Values are rounded to 6 significant digits; labels such as host_*, telemetry_sdk_* and service_instance_id are dropped, and __name__ is shown as metric.

7.6 Trend, and the bug that live data revealed

def _trend(values):
    if len(values) < 2: return "insufficient_data", None, None
    k = max(1, len(values) // 4)
    early, recent = statistics.median(values[:k]), statistics.median(values[-k:])
    if max(values) == min(values): return "flat", early, recent
    relative = (recent - early) / max(abs(statistics.fmean(values)), 1e-12)
    return ("increasing" if relative > 0.10 else "decreasing" if relative < -0.10 else "flat"), early, recent
Why not linear regression?Version 1 fitted a least-squares line over the whole window with a 5 % threshold. Unit tests passed, but the first run against live data returned checkout p95 latency as trend: "increasing" next to change: -25.6%, and product-catalog rate as "decreasing" next to +0.5%. The raw series showed the cause: latency oscillated between 34 and 50 ms (dip at 5–10 min, rise at 20 min), and the regression line followed that mid-window shape. Quarter medians describe "where it started vs where it is now", ignore single spikes, and come with the two medians that justify the verdict. A property test now checks, on every recorded real series, that the verdict agrees with those medians.

10. Testing

Strategy

  1. Record: scripts/record_prometheus_fixtures.py issued 10 real range queries (30 min, 15 s step) and saved each request and raw response (status, content type, body).
  2. Replay: a pytest fixture serves a recording through httpx.MockTransport and records every outgoing request, so tests check behaviour and also confirm that nothing else was sent (method, path, parameters, number of calls).
  3. Synthesise only what can't be recorded: transport exceptions, specific trend shapes, oversized bodies, unknown error types.
  4. Live: 4 tests against the real Prometheus, auto-skipped when /-/ready doesn't answer.

13. Interview questions

1. Instant query vs range query?
An instant query (/api/v1/query) evaluates once and returns a vector. A range query (/api/v1/query_range) evaluates at each step from start to end and returns a matrix. Trends need a range query.
2. What do step and lookback-delta do?
Step is the spacing of evaluation timestamps. At each one, Prometheus uses the newest sample within lookback-delta (5 m). A step smaller than the sample interval just repeats values; we measured 60 s samples and set a 60 s minimum step.
3. Why does rate(x[1m]) return nothing here?
rate needs two samples inside the window. With one sample per 60 s, a 1-minute window usually holds one.
4. How do you get p95 latency from a histogram?
histogram_quantile(0.95, sum by (le) (rate(x_bucket[5m]))): take the rate of each cumulative bucket, keep le while aggregating, and interpolate. It returns NaN when there is no traffic, which is why the tool counts non-finite points.
5. Counter vs gauge?
Counters only increase (reset on restart). Query them with rate/increase. Gauges move both ways and are used directly. Prometheus 3 adds an info annotation when rate() is applied to something that doesn't look like a counter; our tool passes it on.
6. Why summarise instead of returning raw samples to an LLM agent?
Context cost and focus: a 24-hour query of the 18-service request rate returns 18 × 240 = 4,320 (timestamp, value) pairs, while the summary is 18 short records of about 15 fields each. Summaries also encode domain knowledge (NaN handling, trend) consistently instead of leaving it to the model.
7. Why does the tool never raise?
An agent loop should treat failures as information ("the query was wrong", "Prometheus is down") and adapt. Typed error categories let it react differently to a syntax error and an outage.
8. How did you make it read-only, and why isn't "we only call GET" enough?
One private function performs the only network call, with a GET-only allow-list containing a single path, and tests attempt /-/quit and admin paths. It matters because this Prometheus has the lifecycle API enabled. Defence in depth means a future refactor can't accidentally add a write.
9. How do you test code that talks to an external service?
Record real responses once, replay them through the HTTP library's transport layer, and assert on outgoing requests too. Add a small live suite that skips when the dependency is absent. Recordings caught details mocks would have missed: string-encoded NaN, infos vs warnings, and a 422 message that leaked a flagd label.
10. Why median-of-quarters for trend rather than regression or first-vs-last?
First-vs-last depends on two possibly noisy points. Regression is sensitive to shape: on live data it said "increasing" while the series ended 25 % lower. Quarter medians resist single spikes, summarise the start and end of the window, and come with the numbers that justify the verdict.
11. How do you stop an agent learning the injected fault from metrics?
Layered controls: refuse flag-related query text, ban __name__ and metric-less selectors (obfuscation and sweeping), scrub flag-labelled series from results, redact error text, and never report how much was hidden. The system-wide fix is a gateway that strips the data before it reaches a store agents can query.
12. Why ignore HTTP_PROXY?
Observability data is internal. Sending queries and results through a third-party (here, college) proxy leaks them and adds a failure point. Explicit configuration beats implicit environment.
13. What would you change for production?
Authentication (bearer token or mTLS), a shared client with connection pooling, retries with backoff only for idempotent 503s, metrics about the tool itself (latency, error types), caching for repeated agent queries, and enforcing flag isolation at the gateway rather than per tool.
14. What is high cardinality, and how does the tool handle it?
Many label combinations mean many series. The tool caps the response at 10 MiB, returns at most max_series summaries with truncated set, and encourages aggregation via its error messages.

14. Limitations, files and next steps

Known limitations

  • Trend is a direction label, not anomaly detection; it has no baseline or seasonality. That comes with the detection work.
  • Units aren't inferred; they are implied by metric names (_bytes, _milliseconds, _ratio).
  • Sorting by latest can hide a series that spiked earlier but has since recovered; callers can raise max_series.
  • The regex guard is heuristic; residual aggregate side channels are described in §11.
  • No Git commit was made: the project root isn't a Git repository (D-110). A .gitignore is ready.
