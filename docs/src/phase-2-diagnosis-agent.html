1. The idea in one minute

In Week 1 we built three hands: query_metrics reads numbers (Prometheus), search_logs reads what services write (OpenSearch), and get_traces follows one request across services (Jaeger). A human called them and decided what was wrong.

In Week 2 we added a brain and an alarm:

  • The brain is a Gemini model inside a Google ADK agent. It decides which tool to call next, reads the result, and repeats until it can name the root cause with evidence.
  • The alarm is a small Python program with no AI in it. It watches error ratios and, when a service stays broken for 2 minutes, wakes the brain with an alert.
AnalogyThe tools are the stethoscope and blood test. The agent is the doctor who decides which test to run next. The detector is the heart monitor that beeps and calls the doctor.

3. Architecture

One incident, start to finish (what happens in code)

  1. Fault: we set paymentFailure=50%; half of the payment charge calls fail.
  2. Detector polls every 15 s. Payment and checkout error ratios go above 5 %. After 2 minutes it builds one alert text naming the breaching services.
  3. diagnose(alert) creates an ADK session and sends the alert to the agent.
  4. The agent loops: Gemini asks for a tool, ADK runs the Python function, the result goes back to Gemini, and this repeats (section 5).
  5. The answer comes back as JSON matching the Diagnosis schema. It is printed and saved to runs/ with the full transcript, token count and latency.

4. How ADK uses our tools (and why not MCP)

We pass plain Python functions to the agent. That is all:

agent = LlmAgent(
    name="diagnosis",
    model="gemini-2.5-flash",                       # from $COPILOT_MODEL
    instruction=lambda ctx: load_prompt("diagnosis"),
    tools=[get_service_health, get_service_metrics, get_traces, search_logs, query_metrics],
    output_schema=Diagnosis,                        # final answer must be this JSON
    before_tool_callback=tool_guard,                # allow-list + budget
)
  1. ADK reads each function and wraps it as a FunctionTool: name, type hints and docstring become the tool description Gemini sees. So our Week-1 docstrings are now part of the prompt.
  2. Gemini cannot run code. It replies with a request such as get_traces(service="checkout", errors_only=True).
  3. ADK runs our real function in our own Python process. The function makes the GET request to Jaeger, summarises and filters the result.
  4. ADK sends the result dict back to Gemini, which decides the next step.
Why not MCP?MCP (Model Context Protocol) is for tools that live in another process or system, for example a customer's Datadog MCP server. Our tools are in the same Python program, so a direct function call is simpler, faster and easier to test. ADK does support MCP (McpToolset), so exposing copilot/tools as an MCP server is a possible Week-6 extra: the same tool layer could then plug into any MCP client.

5. The ReAct loop in action

ReAct = Reason + Act. The agent thinks about what to check, calls a tool, reads the result, and repeats. Below is a real run of the ADK loop against the live demo with paymentFailure=50%. The tool calls and results are real. The decisions came from a scripted test model, because no Gemini key was set during the build; Gemini makes the same kind of decisions itself.

ALERT error ratio above 5% for at least 2 minutes. Breaching services: checkout, payment.

ACT     get_service_health(minutes=15)
OBSERVE get_service_health -> ok (4.1 KB)
          services_with_observations: ["payment", "checkout"]
          top_services: ["payment: error ratio 35% now vs 50% at window start", "checkout: ..."]
ACT     get_traces(service='checkout', errors_only=True, minutes=15, limit=5)
OBSERVE get_traces -> ok (12.0 KB)
          error_origins: {"payment :: charge": 5}        <- every failure STARTS in payment
ACT     get_service_metrics(service='payment', minutes=15)
OBSERVE get_service_metrics -> ok (0.6 KB)
          top_operations: ["oteldemo.PaymentService/Charge: error ratio 35% now vs 50% ..."]
ACT     search_logs(service='payment', level='warn', minutes=15)
OBSERVE search_logs -> ok (8.8 KB)
          top_patterns: ["payment/warn: Payment request failed. Invalid token. ... x16"]
SUBMIT  final answer
ANSWER  root cause: payment (errors, confidence high)
        summary: Payment charge calls fail; checkout errors are a downstream symptom.

How to read it: metrics show that payment and checkout are failing, but both have the same error ratio, so metrics alone cannot say which one is the cause. Traces show where failures start (payment :: charge). Logs show what payment reports. Three signals agree, so confidence is high.

6. New tools: get_service_health and get_service_metrics

Why we added them

With only query_metrics, the model would have to write PromQL itself. LLMs often write PromQL that is wrong, for example service instead of service_name, or a missing rate(). Then the tool says no_data and the model may conclude "nothing is wrong". So we wrapped three tested queries (the "golden signals") behind simple parameters.

SignalPromQL inside (simplified)
Traffic (req/s)sum by (service_name) (rate(traces_span_metrics_calls_total{span_kind=~"SERVER|CONSUMER"}[2m]))
Error ratio (%)100 * (errors or 0 * total) / total; the or 0 * total gives healthy services an explicit 0 % instead of a gap
p95 latency (ms)histogram_quantile(0.95, sum by (le, service_name) (rate(..._duration_milliseconds_bucket[2m])))

Example: one row of the real output (payment fault on)

{"service": "payment",
 "requests_per_sec": {"now": 0.042, "window_start": 0.058, "max": 0.067},
 "error_pct":        {"now": 50.0,  "window_start": 70.8,  "max": 100.0},
 "p95_ms":           {"now": 2.8,   "window_start": 2.9,   "max": 9.7},
 "observations": ["error ratio 50% now vs 70.8% at window start"]}
  • now / window_start = median of the last / first quarter of the window. Medians stop one noisy sample from changing the picture.
  • observations are plain comparisons such as "error ratio 50% now vs 0% at window start". They describe symptoms; they never name a cause.
  • Only SERVER and CONSUMER spans are counted, so each service is measured on the work it receives, and the load generator (client spans only) drops out.
  • Unhealthy services come first, and the whole overview is about 4 KB instead of hundreds of raw series.
  • get_service_metrics("payment") shows the same signals per operation, here oteldemo.PaymentService/Charge.
  • Both are wrappers around query_metrics, so they inherit its read-only HTTP path, flag filters and "never raise" contract. flagd as a service name is refused.

7. The prompt (copilot/prompts/diagnosis.md)

Method

1. Overview with get_service_health. 2. Symptom vs. cause: follow traces, read error_origins. 3. Confirm in the suspect (metrics per operation, logs). 4. Check timing. 5. Stop after ~12 calls.

Lessons from Week 1

Search logs with level="warn", not "error": payment logs its failures as warnings, so "error" returns nothing during a real incident.

PromQL cookbook

Exact queries to copy for raw query_metrics calls, with correct label names and [2m] windows.

Evidence and honesty

2–6 evidence items quoting real values, trace IDs copied exactly, confidence rules, and "no incident" is a valid answer.

Two design details: the prompt never mentions feature flags (a test checks this), and it is passed to ADK as a function, because ADK would otherwise treat {...} in the PromQL examples as template placeholders.

8. The structured answer

The agent must end with JSON that matches a Pydantic schema. ADK validates it.

{"incident": true,
 "root_cause_service": "payment",
 "failure_type": "errors",            // errors | latency | resource | queue_lag | traffic_spike | unavailable | none | unknown
 "confidence": "high",                // high only when metrics, traces and logs agree
 "summary": "Payment charge calls fail; checkout errors are a downstream symptom.",
 "affected_services": ["checkout", "frontend"],
 "evidence": [{"kind": "trace", "detail": "error_origins payment :: charge x5"},
              {"kind": "log",   "detail": "payment warn 'Payment request failed' x16"}],
 "alternative_causes": ["checkout"],
 "suggested_next_checks": ["recent payment deploys"]}
Why structured, not free text?In Week 5 a script will inject a fault, run the agent and compare root_cause_service with the known answer automatically. Free text cannot be scored. alternative_causes gives a "right answer in top 3" metric, and incident: false lets us score false alarms.

9. Safety rules in the agent

RuleHow it is enforced
Read-onlyOnly the 5 read tools are attached. No flag, shell, HTTP or write tool exists for this agent. The agent cannot hand work to other agents.
Allow-list (defence in depth)before_tool_callback refuses any tool name outside TOOLS, so a model that invents set_feature_flag gets an error and nothing runs.
BudgetAfter 15 tool calls the guard returns budget_exhausted: "answer with what you have". This caps cost and stops loops.
No answer leakageAll telemetry still passes through filters.py; the prompt and alert never mention flags (tests check both).
SecretsThe Gemini key lives in .env, which is git-ignored; .env.example documents it.

10. The detector (the alarm)

Version 1 is a simple rule with no AI: error ratio > 5 % for 2 minutes, ignoring services with almost no traffic, then a 10-minute cooldown. All breaching services go into one alert, because failures cascade: payment and checkout breaking together is one incident, not two.

The logic is a small state machine (ThresholdDetector.observe(now, readings)) with no network calls, so it is easy to test: "4 bad readings in a row fire", "a blip resets the clock", "cooldown holds".

Real dry run with the payment fault on

watching: error ratio > 5% for 120s, poll 15s, cooldown 600s (dry run)
12:18:25  services above 5%: {'checkout': 30.8, 'payment': 30.8}
12:19:10  services above 5%: {'checkout': 40.0, 'payment': 40.0}
12:20:11  services above 5%: {'checkout': 42.9, 'payment': 42.9}
ALERT (automated detector): error ratio above 5% for at least 2 minutes.
Breaching services: checkout 42.9%, payment 42.9%. Breach started 12:18:25 UTC,
alert fired 12:20:26 UTC. Investigate and find the root cause.
12:20:41  services above 5%: {...}        <- no second alert (cooldown)
A real-world lesson: low traffic makes ratios noisyAt first the detector used a 2-minute window. The demo sends only about 1 checkout per minute, so over 2 minutes payment's error ratio jumped between 0 % and 100 %, and one poll read 0 % while the fault was still on. That would reset the "2 minutes in a row" clock and delay or miss the alert. Fix: the detector smooths over 5 minutes (it then read 31–43 % steadily). The agent's tools keep 2 minutes because the agent needs to react quickly and also reads traces and logs.

Version 2 (later): replace the fixed 5 % with a learned normal band (rolling mean ± 3 standard deviations) so latency faults, which barely change error ratios, are caught too.

11. Testing an AI agent without calling the AI

Calling Gemini in unit tests would cost money, hit rate limits and give different answers each run. So we wrote ScriptedLlm: a fake model (a subclass of ADK's BaseLlm) that plays back a fixed list of turns, such as "call get_service_health", then "call get_traces", then "here is the JSON". The real ADK loop runs: it calls our real tool functions (backends are offline in unit tests, so they return clean error dicts) and validates the answer.

Test areaExamples of what is checked
Agent setup (26 tests)Exactly the 5 read tools; no transfer; prompt loaded verbatim; prompt has the warn lesson and no flag words; both answer paths; budget stops a looping model; unknown tools never run; quota errors keep the transcript; invalid answers are reported, not raised.
Health tools (33 tests)Merging the 3 signals; unhealthy first; observation thresholds; bad input refused before any query; flagd forbidden; flagd series dropped; 3 GET requests to /api/v1/query_range.
Detector (11 tests)Fires only after 2 minutes; one alert per incident; blips reset; cooldown; idle services ignored; 5-minute queries; survives metric errors.
Live (3 new)Overview covers the shop and hides flagd; per-service detail; detector readings on real Prometheus.

12. Bugs and surprises we found

1. The "invisible" error logs (from Week 1 testing)
search_logs(level="error") returned nothing during the payment fault, because payment logs failures as warnings. Now in the prompt: always use level="warn".
2. ADK's hidden answer tool
With an AI Studio key, ADK cannot combine tools and an output schema natively. Reading the ADK 2.15 source showed that it then adds an internal tool, set_model_response, which the model calls to hand in its JSON. Our allow-list guard would have blocked the final answer. Fixed (the guard lets that one tool through without counting it) and covered by a test that simulates this mode.
3. A newline sneaking into PromQL
Service names were checked with re.match(r"^...$"). In Python, $ also matches before a trailing newline, so "payment\n" passed and would have been pasted into a PromQL query. A parametrised test caught it; fixed with fullmatch.
4. Noisy ratios at low traffic
Section 10: 2-minute error ratios swung between 0 % and 100 %. The detector now uses 5 minutes.
5. Noisy latency notes
fraud-detection showed "p95 latency 2.1x higher" from about 2 requests a minute. Latency observations now need at least 0.05 req/s.
6. Braces in the prompt
ADK fills {name} placeholders in string instructions from session state. PromQL is full of braces, so the prompt is passed as a function, which ADK uses as-is.

13. Status, how to run it, limitations

Honest statusEverything is built and tested (427 tests, including live ones on a real fault). The one thing not yet measured is how often Gemini names the right cause, because no API key was configured during the build. The Week-2 target, "the single agent finds the payment fault most of the time", is checked with run_diagnosis.py --runs 5. Until that runs, do not quote an accuracy number.

Run it yourself

  1. Get a free key at aistudio.google.com/apikey, then cp .env.example .env and paste it as GOOGLE_API_KEY.
  2. Start the demo (scripts/start_demo.sh) and turn on paymentFailure=50% at localhost:8080/feature. Wait 3 minutes.
  3. .venv/bin/python scripts/run_diagnosis.py --runs 5 prints every step and a tally such as "payment x4, checkout x1".
  4. .venv/bin/python -m detector.watcher waits for the alert, then the agent investigates by itself.
  5. Turn the fault off and run once more: the agent should answer incident: false.

Limitations (known, planned)

  • One generalist agent; the Coordinator plus specialist team arrives in Week 4.
  • No runbooks or past incidents yet (RAG, Week 3).
  • The detector only catches error faults; latency and memory faults need version 2.
  • The alert names all breaching services. For a fair evaluation in Week 5 we may limit it to the user-facing service, so the alert does not hint at the answer.
  • No session storage (in-memory) and no approval flow yet (Week 4).

14. Interview questions and answers

How does your agent call the observability tools? Is it MCP?
No. ADK wraps plain Python functions as FunctionTools, using their type hints and docstrings as the schema. Gemini asks for a call, ADK runs the function in-process, and the result goes back to the model. MCP would make sense if the tools lived in another system, for example a customer's existing MCP server. Our tool layer could be exposed as one later.
The LLM has to write PromQL. Isn't that fragile?
Yes, so the agent mostly doesn't. I added get_service_health and get_service_metrics, which run tested golden-signal queries and return a compact table with plain observations. Raw PromQL is a fallback for unusual questions, and the prompt includes a cookbook of correct queries.
How does it tell symptom from cause?
Metrics often can't: during the payment fault, checkout and payment had identical error ratios. The agent follows traces and reads error_origins, the deepest failing span, which pointed at payment :: charge in every failed trace. Logs then confirm it.
How do you stop it inventing a root cause?
Structured output with mandatory evidence quoting real values or trace IDs, confidence rules (high only if three signals agree), "no incident" as a valid answer, and in Week 4 a Reviewer agent. In Week 5 I measure the evidence-grounded rate.
How do you test something non-deterministic?
I split it. Deterministic parts (tools, guard, parsing, detector, the ADK loop itself) are tested with a scripted fake model, so there are no API calls and no flakiness. The model's judgement is measured separately with repeated runs on injected faults, where the true cause is known.
What stops the agent from doing something dangerous or expensive?
It only has read tools; a callback enforces an allow-list and a 15-call budget; it cannot transfer to other agents; and all telemetry goes through a GET-only, filtered HTTP layer.
How do you know it isn't cheating?
The faults are injected with feature flags, and the flag state leaks into telemetry. The filter removes it from every tool output (tested on data recorded during real faults), no tool can reach flagd, and the prompt and alert never mention flags.
Why does the detector have no AI?
Detection must be cheap, predictable and always on. A threshold with a duration and cooldown is easy to reason about and test. The expensive LLM runs only once per incident. Version 2 will learn a normal band per metric, which is where my anomaly-detection background comes in.
What surprised you?
Real data issues: failures logged as warnings, error ratios that swing from 0 % to 100 % at low traffic, and ADK's hidden set_model_response tool, which my own safety guard would have blocked. All three were found by running against the real system and reading the framework source, not by assuming.
What would change for a real customer?
Swap the tool layer for their stack (Cloud Monitoring, Datadog), keep the same function signatures, adapt the golden-signal queries to their metric names, give the tools read-only service accounts, and run the same evaluation on their past incidents before going live.
